# Gateway Switch v1.14.0 Provider 配置向导与一键健康检查 PRD

## 1. 背景

Gateway Switch 已经具备 Provider Presets、Provider 兼容性策略、Claude/Codex Gateway 路由、Unified Diagnostics、Gateway Health Check 等基础能力。当前问题是这些能力仍然偏“专家工具”：

- 新用户需要理解 OpenAI Base URL、Anthropic Base URL、auth header、auth scheme、Claude alias、Codex model、upstream model、策略覆盖等概念，配置成本高。
- Provider Presets 已能创建 Provider 和写入推荐策略，但缺少端到端向导，用户不知道下一步是否要创建路由、是否要绑定 Claude/Codex、是否配置成功。
- 健康检查目前分散在 Claude、Codex、Provider 单点按钮中，缺少一次性验证完整链路的能力。
- 国内和第三方模型 Provider 的失败原因高度相似，但用户看到的往往只是 HTTP 400/401/404/429/5xx，缺少面向行动的诊断。

v1.14.0 聚焦两个功能：

- Provider 配置向导
- 一键健康检查

目标是把“新增一个可用 Provider”从专家级手动配置，降低为一个可验证、可回滚、可诊断的向导流程。

## 2. 产品目标

### 2.1 主目标

让用户在 3 分钟内完成一个 Provider 的配置、路由生成和基础健康验证，并知道它是否适合 Claude Desktop、Claude Code 和 Codex。

### 2.2 体验目标

- 用户不需要先理解所有协议细节，也能完成配置。
- 向导每一步都告诉用户“正在配置什么、为什么需要、失败后如何修复”。
- 一键健康检查能同时验证本地 Gateway、Provider 认证、Provider 模型列表、Claude Route、Codex Route。
- 结果必须能落到明确状态：通过、警告、失败、跳过。
- 失败结果必须给出下一步建议，而不是只显示原始错误。

### 2.3 工程目标

- 复用 v1.12.0 Provider Presets 和 v1.13.0 Diagnostics/Loop Guard 基础设施。
- 不引入自动写入外部客户端配置的隐式副作用。
- 不自动发起 token 消耗型 chat completion，除非用户明确选择“深度检查”。
- 所有 API Key、Authorization header、响应 body 中的密钥必须脱敏。

## 3. 用户画像

### 3.1 新手用户

用户有某个 Provider 的 API Key，希望让 Claude Desktop、Claude Code 或 Codex 使用这个 Provider，但不知道该填哪个 Base URL 或模型名。

需求：

- 选择 Provider 模板
- 粘贴 API Key
- 看到推荐模型和推荐入口
- 一键检查是否可用

### 3.2 高级用户

用户已经理解不同协议，希望快速批量验证多个 Provider 和 route 是否仍然健康。

需求：

- 对所有 Provider 批量健康检查
- 查看失败聚合和建议
- 保留手动编辑能力
- 导出诊断结果

### 3.3 后续 AI Agent

AI Agent 需要根据文档快速实现 v1.14.0，不破坏已有 v1.12/v1.13 兼容逻辑。

需求：

- 明确数据模型和命令边界
- 明确非目标和安全规则
- 明确测试矩阵

## 4. 范围

### 4.1 Provider 配置向导

新增 Provider Wizard，用于从 Provider Preset 创建或更新 Provider，并引导用户完成基础配置。

向导步骤：

1. 选择 Provider
   - 展示 built-in presets：OpenRouter、Volcengine Ark DeepSeek、DeepSeek、Moonshot、Qwen、Xiaomi MiMo、Anthropic-compatible、OpenAI-compatible Chat。
   - 展示每个 preset 的协议能力、推荐用途、风险提示。
   - 支持“自定义 Provider”入口。

2. 填写凭据和端点
   - API Key
   - OpenAI Base URL
   - Anthropic Base URL，可选
   - Auth Header
   - Auth Scheme
   - Provider 名称
   - 上游模型名

3. 推荐策略确认
   - 展示推荐 compatibility policy。
   - 用自然语言解释每个策略的作用，例如 system_to_user、tool_to_user、strip_unsupported_params、codex_chat_fallback、codex_strict_tool_calls。
   - 默认使用 preset 推荐策略。
   - 高级用户可展开修改。

4. 推荐路由生成
   - 生成 Claude Route 草案。
   - 生成 Codex Route 草案。
   - 支持只创建 Provider，不创建 route。
   - 支持覆盖默认 alias/model 名称。

5. 健康检查
   - 自动运行轻量健康检查。
   - 展示 Provider、Claude Gateway、Codex Gateway、Route 配置状态。
   - 检查失败时给出修复建议。

6. 完成页
   - 展示配置摘要。
   - 给出下一步行动：绑定 Claude Desktop、绑定 Claude Code、绑定 Codex、打开 Diagnostics。

### 4.2 一键健康检查

新增 One-Click Health Check，用于统一检查 Gateway Switch 的 Provider 接入链路。

检查对象：

- App runtime
- Claude Gateway 本地 `/health`
- Codex Gateway 本地 `/health` 或 `/v1/responses` 健康入口
- Provider `/models`
- Claude routes
- Codex routes
- Provider compatibility policy
- Recent failure clusters

检查模式：

- Quick Check：默认模式，只做低成本检查，不消耗模型 tokens。
- Deep Check：可选模式，用户明确确认后，针对指定 route 发送最小化 completion 请求验证真实响应能力。

v1.14.0 默认只要求实现 Quick Check。Deep Check 可在 UI 中预留入口，但不作为必须上线项。

### 4.3 结果展示

健康检查结果需要包含：

- 总体状态：healthy、attention、degraded、critical
- 总分：0-100
- 每项检查状态：pass、warn、fail、skipped
- 延迟：latency_ms
- HTTP 状态码
- 脱敏错误摘要
- 推荐修复动作
- 是否可自动修复
- 关联对象：provider_id、route_id、surface

## 5. 非目标

- 不在 v1.14.0 中迁移 API Key 到 macOS Keychain。
- 不自动绑定 Claude Desktop、Claude Code 或 Codex，除非用户点击已有绑定按钮。
- 不默认发送真实 chat completion。
- 不自动修改用户手工配置的 route，除非用户在向导里确认创建或更新。
- 不引入云端 Provider Profile 同步。
- 不实现批量导入第三方 Provider 列表。
- 不保证所有 Provider 的 `/models` 端点都存在；不存在时应降级为可解释 warning。

## 6. 用户故事

### 6.1 从 Preset 添加 Provider

作为新用户，我希望选择“小米 MiMo”模板、粘贴 API Key，然后自动生成推荐配置，这样我不用理解所有协议细节。

验收标准：

- 用户可以从 Providers 页面打开 Provider Wizard。
- 用户选择 preset 后，表单自动填充推荐 Base URL、auth header、auth scheme、推荐模型。
- 用户可以看到该 preset 的风险提示。
- 用户点击完成后，Provider 被创建或更新。
- 如果 API Key 留空且已有 Provider 有 Key，不覆盖旧 Key。

### 6.2 生成推荐路由

作为用户，我希望配置 Provider 后能同时生成 Claude 和 Codex 路由，这样我可以马上在客户端里使用。

验收标准：

- 向导展示 Claude Route 和 Codex Route 草案。
- 用户可以选择创建两者、只创建 Claude、只创建 Codex、或都不创建。
- 已存在相同 id/alias 时，UI 必须提示将更新还是跳过。
- 生成 route 后，Dashboard 和对应页面能看到新配置。

### 6.3 一键健康检查

作为用户，我希望点击一个按钮检查当前所有 Provider 和路由是否可用，这样我不用逐个页面排查。

验收标准：

- Diagnostics 页面新增 One-Click Health Check 入口。
- Providers 页面也提供针对单个 Provider 的 Check 按钮。
- 检查完成后展示总体状态和分项结果。
- 401/403 显示凭据错误建议。
- 404 显示 Base URL 或 endpoint 可能错误建议。
- 429 显示限流/额度建议。
- 5xx/network 显示 Provider 可用性建议。
- role/tool/reasoning 类错误能映射到 compatibility policy 建议。

### 6.4 导出健康检查结果

作为高级用户，我希望导出健康检查结果，用于发 issue 或交给 AI Agent 继续分析。

验收标准：

- 导出 JSON bundle。
- Bundle 不包含明文 API Key、Authorization header、完整请求 body。
- Bundle 包含检查时间、应用版本、Provider id、route id、状态、建议动作。

## 8. 健康评分规则

基础规则：

- 所有必需检查通过：100
- Provider `/models` 失败但 route 配置完整：最高 75
- Gateway 本地 health 失败：最高 60
- API Key 认证失败：最高 50
- route 缺失或 disabled：最高 70
- 无 Provider：最高 30
- 无法读取数据库或配置：最高 20

状态映射：

- 90-100：healthy
- 70-89：attention
- 40-69：degraded
- 0-39：critical

## 9. 安全与隐私

- API Key 输入框默认 password 模式。
- 日志和导出结果必须使用已有 redact 逻辑。
- 健康检查不记录完整 Authorization header。
- Quick Check 不发送用户 prompt。
- Deep Check 必须有明确确认文案。
- Provider Wizard 不自动写入 Claude/Codex 外部配置。
- 对 risky provider 的 Claude Code Direct Provider 仍然要求显式确认，不因向导绕过。

- Provider 配置失败时，用户能获得至少一个可执行建议。
